# RFC 0002：公開發表與授權

- 狀態：Accepted（2026-11-01）；待決問題 1 已決定（2026-11-03，A1：公開現有 repo，不改寫 git 歷史）
- 日期：2026-11-01
- 決定者：@BenTsai0212
- 相關：RFC 0001（本 RFC 修訂其第 2 階段的內容與順序）、Epic #3（第 1 階段完成）

## 摘要

knowledge-kit 定位為**通用的第二大腦 demo template**，作為個人作品與後續商業發展的對外發表；它不依附任何特定客戶，客戶的需求是它的應用之一。

第 1 階段的成果直接作為**第一個公開版本（v1）**發表：以 **MIT 授權**公開，附一個**線上可以直接試用的 demo**，`README.md` 以英文為主、另附繁中。公開前先完成授權、git 歷史中的個人 email、內容與歷史的稽核、公開文件與線上 demo。多語言（跨語言檢索、泰文等不以空白分詞的語言）作為**下一個版本（v2）**，以虛構的多語言情境實測，不等待任何客戶。開發流程工具（`tools/workflow/`、runner、`.claude/` 指令、`docs/workflow/`）與 demo 套件一起公開。

## 問題與使用者

- RFC 0001 規定：先自己用，驗證後整理成公開版本，授權與公開時程另開 RFC 決定。第 1 階段已完成，門檻 1～5 實測通過（#88）。
- RFC 0001 原本把第 2 階段寫成「以第一個多語言客戶的 fork 實測」。實際上目前沒有提出需求的客戶，只有要 pitch 的潛在客戶；把發表綁在客戶身上會讓時程無限期延後。所以本 RFC 修訂第 2 階段：先發表，多語言改用虛構情境實測。
- 發表的對象：
  - 想為客戶快速做出「第二大腦」demo 的開發者
  - 想參考「交給 coding agent 照文件做」這套做法的人
  - 潛在客戶與合作夥伴：線上 demo 讓他們不用安裝就能試用
- 為潛在客戶做的 pitch demo 是各自的 fork，不屬於本 RFC 的範圍；客戶與夥伴的名稱不進 template。

## 提案

### 1. 授權：MIT

- 新增 `LICENSE`（MIT），著作權人為 `BenTsai0212`，年份 2026。
- `README.md`、`package.json` 的 `license` 欄位一併標示。
- 理由：最寬鬆、最常見，使用者可以自由使用、修改與商用，只需保留版權聲明；符合「擴大影響力」的目標。不防止他人拿去做商業服務，這點接受。

### 2. git 歷史中的個人 email

現況（2026-11-01 檢查）：

- `Initial commit` 與所有在 GitHub 上合併的 squash commit（目前 61 個），作者 email 都是帳號的主要個人 email；agent 推送的 commit 已使用 GitHub noreply。
- 原因：在 GitHub 上合併 PR 時，作者使用帳號的主要 email。

處理：

1. **立即**：在 GitHub 帳號設定開啟「Keep my email addresses private」（與「Block command line pushes that expose my email」），之後網頁與 API 的合併改用 noreply。由人在 GitHub 設定中操作。
2. **改寫歷史（不採用）**：原本提案以 `git filter-repo` 的 mailmap 把個人 email 換成 noreply，全部分支一起改寫後強制推送。依待決問題 1 的決定（A1），**不改寫歷史**，接受舊 commit（62 個）中的作者 email 可見；PR #94 起的 commit 已是 noreply。
3. **已知限制**：GitHub 會保留每個 PR 的 `refs/pull/<編號>/head`，即使改寫，舊 commit 仍可從 PR 取得，個人 email 也就仍可見。這是不採用改寫的原因之一（見「待決問題」1）。

### 3. 內容與歷史的稽核

公開前確認目前的檔案與整段 git 歷史都沒有：

- 真實客戶名稱、合作夥伴品牌名稱：以 `SENSITIVE_NAMES` 清單掃描**整段歷史**（目前 CI 只掃描檔案），由人在本機執行，清單不進 repo。
- 金鑰：gitleaks 已掃過整段歷史（#66），公開前再跑一次。
- 個人路徑與帳號資訊：例如 `/Users/<名稱>`、本機資料夾名稱、個人 email。
- 設計語言：確認介面使用的設計語言可以公開（若參考了合作夥伴的設計，取得同意）。
- Issue 與 PR 的文字：依待決問題 1 的決定（A1）公開現有 repo，所以所有 Issue 與 PR（含已關閉）的標題、描述、留言、review 與它們的**編輯紀錄**也要稽核，不得有客戶與夥伴名稱、個人路徑與個人 email。GitHub 會保留編輯紀錄，只改現在的內容不夠，命中的版本要刪除。以 `npm run check:sensitive -- --github` 由人在本機執行（#111，見 `docs/testing.md`「GitHub 模式」）；已知 PR #98 的描述與 #100 的計畫留言的第一版誤貼了其他專案的內容（#104）。

### 4. 公開用的說明文件

- `README.md`（英文）與 `README.zh-TW.md`（繁中），內容一致：
  - 這是什麼：通用的第二大腦 demo template；demo 是展示用原型，不是正式系統
  - 線上 demo 的網址與試用方式
  - 畫面截圖
  - 快速開始：安裝、以參考情境啟動、建立第一個客戶（連到 playbook）
  - 資料安全：demo 的資料全部在瀏覽器，權限是「展示用權限」（連到資料安全說明）
  - 開發流程：怎麼交給 coding agent（連到 `docs/workflow/`）
  - 支援的語言與路線圖（v2：跨語言檢索與更多語言）
- `SECURITY.md`：回報安全問題的方式。
- 流程工具：檢查 `tools/workflow/`、`.claude/`、`docs/workflow/` 中的帳號、路徑與個人化設定，改成可替換的設定或範例值。
- 不新增：`CONTRIBUTING.md`、行為準則；公開後有外部參與時再補。

### 5. 線上 demo

修訂 RFC 0001「不做什麼」中的「部署給外部使用者的參考網站」：v1 發表包含一個以參考情境運作的線上 demo。

- 網頁部署為靜態網站，`/api/ask` 部署為 Worker，沿用現有的邀請碼與每日次數上限（`DAILY_LIMIT`）。
- 先以 plan-first 決定：訪客怎麼取得試用額度（公開的共用額度，或索取邀請碼）、模型費用的每日與每月上限、超過上限時畫面怎麼顯示。
- 部署屬於新增外部服務與 secret（AGENTS.md 第 6 節：先問人）；金鑰只放在 Worker secret。
- 畫面與 README 標示「虛構資料」「展示用權限」。

## 不做什麼

- 不在 v1 處理多語言（跨語言檢索、泰文）：列為 v2，以虛構的多語言情境實測（比照 #83 的日文實測），先以 plan-first 評估語意向量的做法（瀏覽器內模型與外部 API）。不等待任何客戶。
- 不在 template 中放任何潛在客戶的 pitch demo；那些是各自的 fork。
- 不接受外部貢獻流程、不建立社群管道。
- 不改授權以外的商業安排。

## 階段與門檻

**v1 發表**（第 2 階段前半）的門檻：

1. `LICENSE`（MIT）與公開用 `README.md`、`README.zh-TW.md`、`SECURITY.md` 已合併
2. 新的 commit 不再出現個人 email；歷史中的 email 依待決問題 1 的決定（A1）保留
3. 稽核通過：整段歷史的敏感名稱掃描與 gitleaks 都是 0；流程工具中沒有個人路徑與帳號資訊；Issue／PR 的文字與編輯紀錄的掃描是 0
4. 設計語言可公開使用（已確認）
5. 線上 demo 可以使用，且有模型費用上限
6. CI 通過

全部通過後，由人以 `## 決定` 把 repo 設為公開（或建立公開 repo）。

**v2 多語言**（第 2 階段後半）的門檻在 v2 的計畫中另訂，至少包含：虛構多語言情境的跨語言評測題通過驗收指標、新增語言的步驟文件依實測更新。

## 待決問題

1. **公開方式**（因為 PR 的 ref 會保留舊 commit）：**已決定（2026-11-03，見 Epic #93 的 `## 決定`）：採 A1，公開現有 repo，不改寫 git 歷史。**
   - 選項：
     - **A1. 公開現有 repo，不改寫歷史**：保留所有 Issue 與 PR；舊 commit 中的個人 email 可見。
     - **A2. 公開現有 repo，改寫歷史**：以 `git filter-repo` 改寫後強制推送，再公開現有 repo。
     - **B. 另開公開 repo**：把改寫後的歷史推到新的公開 repo，現有 repo 保持私人，繼續當開發用。
   - 採用 A1 的理由：
     - 保留所有 Issue 與 PR，決策紀錄完整呈現；文件中的 `#編號` 連結維持有效。
     - 舊 commit（62 個）中的作者 email 可見，接受這個曝光；PR #94 起的 commit 已是 noreply。
     - 代價：Issue 與 PR 的文字與編輯紀錄也要稽核（見提案 3，#111）。
   - 不採用 A2：GitHub 保留 PR 的 ref，改寫後舊 commit 仍可能可見，達不到目的；而且所有 commit 編號改變、需要強制推送。
   - 不採用 B：公開版看不到 Issue 與 PR 的決策紀錄，文件中的 `#編號` 在新 repo 對不上；還要定期把私人 repo 同步到公開 repo。
