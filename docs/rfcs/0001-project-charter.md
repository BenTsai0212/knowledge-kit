# RFC 0001：knowledge-kit 專案章程

- 狀態：Accepted（2026-10-26）
- 決定者：@BenTsai0212

## 要解決的問題

每次為新客戶準備第二大腦（知識平台）demo，都要從頭改程式、資料與文件；既有的展示原型把資料與知識模型寫死在程式裡，只能服務單一客戶。合作夥伴陸續帶來不同產業的客戶，需要一個能快速換成「該客戶樣貌」的起點。

## 給誰用

- **主要使用者**：Benjamin。為新客戶 fork 本 repo，交給 coding agent 依步驟文件完成 demo。
- **間接使用者**：看 demo 的潛在客戶決策者，以及帶來客戶的合作夥伴。
- **未來**：驗證過後整理成公開版本，給其他開發者使用（授權與公開時程另開 RFC 決定）。

## 第一階段範圍

1. **Demo 套件**（沿用既有展示原型已驗證的功能並重新整理）：
   - 附出處問答、查不到就拒答、引用跳回原文；切換身分看到不同內容（RLS）
   - 知識圖譜、多跳路徑、時間軸
   - 上傳文件、模型萃取、待審與批次核准、矛盾並列
   - 評測台（評測題庫、兩組設定並排比較）
2. **客戶設定檔**：知識模型、角色與權限、示範情境、評測題、語言、品牌色票與字體，集中在 `client/`。換客戶只改設定，不改程式。
3. **參考情境**：一套中立的虛構資料集，作為預設內容與測試基準。
4. **落地新客戶步驟文件**：給 coding agent 照做，每一步有驗收條件。
5. **方法與文件套件**（`docs/playbook/`）：需求確認清單、資料盤點表、評測題庫建立步驟、驗收指標、資料安全說明，以中立寫法撰寫。
6. **中立預設主題**：不使用任何合作夥伴的品牌名稱與 wordmark。
7. **語言**：預設繁體中文與英文。語言清單放在 `client/`；介面文字走翻譯檔，文件帶語言欄位；檢索模組保留「向量提供者」接口。另寫一份「新增語言」步驟文件，涵蓋介面翻譯、內容語言、斷詞與語意向量的選擇（含資料與運算地點的考量），以及跨語言評測題。

## 不做什麼（第一階段）

- 正式系統：伺服器端資料庫、登入、雲端硬碟同步、匯入排程
- 繁中與英文以外的語言、語意向量的實作（只留接口與步驟文件）
- 智慧客服模組、多租戶
- 公開 repo、選定授權條款
- 部署給外部使用者的參考網站（需要時另啟用「上線」模組）
- 任何真實客戶資料、客戶名稱、合作夥伴的品牌名稱

## 階段與門檻

| 階段 | 內容 | 門檻 |
| --- | --- | --- |
| 1. Demo 套件 | 第一階段範圍 1～7 | ① 用一個新的虛構情境（繁中＋英文），照步驟文件在 1～2 個工作天內做出可展示的 demo，且不修改 `client/` 以外的程式；② 該情境的評測：引用正確 ≥ 90%、答案正確 ≥ 80%、權限滲漏 0、題庫外問題正確拒答；③ CI 通過；④ 敏感資料檢查通過（無真實客戶資料、金鑰、個人 email）；⑤ 新增一個語言只需修改 `client/`、翻譯檔與檢索模組（以結構測試或文件檢查確認接口存在） |
| 2. 多語言實測與公開準備 | 以第一個多語言客戶的 fork 照「新增語言」文件加入泰文與跨語言檢索，把遇到的問題修回 template；授權條款、git 歷史清理、公開文件 | 另訂 |
| 3. 正式系統與客服模組 | 抽出正式系統層（伺服器端資料庫、登入、匯入）；客服模組 | 另訂 |

## 錯了的後果

- demo 讓客戶誤以為功能已上線 → 頁面清楚標示「虛構資料」「展示用權限」，對外說法不誇大
- 真實資料或客戶名稱混入 template → 散布到每個 fork，也阻礙公開 → 以硬規則加 CI 檢查擋下
- 權限示範出錯 → 直接損害「權限滲漏 0」的賣點 → 越權測試列為硬性驗收條件

## 標籤

- `phase:1`、`phase:2`、`phase:3`
- `area:site`（網頁）、`area:worker`（模型轉發）、`area:client`（客戶設定與資料集）、`area:playbook`（方法與步驟文件）、`area:workflow`（CI、規則、工具）
