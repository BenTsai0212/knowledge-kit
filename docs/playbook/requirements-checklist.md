# 需求確認清單

第一次和客戶討論 demo 時使用。目的是在動手之前，確認「要展示給誰、展示什麼、誰能看什麼」，避免做出客戶不需要的功能。

每一題的答案最後都會對應到 `client/` 的某個設定檔（右欄），訪談後由我們整理，客戶不需要理解技術細節。

## A. 背景與目的

| # | 問題 | 對應設定 |
| --- | --- | --- |
| A1 | 這次 demo 要給誰看？（例如：老闆、部門主管、IT、全體員工） | — |
| A2 | 看完 demo 後，您希望他們做出什麼決定？（例如：同意試行、編列預算） | — |
| A3 | 目前員工找資料最常遇到的困難是什麼？請舉 2～3 個最近發生的例子。 | `scenarios.json` |
| A4 | 哪些問題最常被重複問？通常是誰在回答？ | `scenarios.json`、評測題庫 |
| A5 | 有沒有已經在用的工具（共用硬碟、雲端文件、Wiki、聊天群組）？ | — |

## B. 公司與知識的樣貌

| # | 問題 | 對應設定 |
| --- | --- | --- |
| B1 | 公司（或要展示的部門）的組織架構：有哪些部門、大約多少人？ | 資料集 |
| B2 | 最常需要查的「東西」是什麼？（例如：人、專案、產品、客戶、設備、規章） | `knowledge-model.json` 的實體類型 |
| B3 | 這些東西之間有哪些重要的關係？（例如：誰負責哪個專案、哪個產品用哪個零件） | `knowledge-model.json` 的關係類型 |
| B4 | 同一件事常有不同的叫法嗎？（例如：中英文名稱、簡稱、代號） | 別名規則 |
| B5 | 有沒有同名但不同的人或東西？ | 合併策略（預設由人確認） |
| B6 | 資料會過時嗎？新舊說法不同時，以哪一份為準？ | 說法不同時並列 |

## C. 權限與機密

| # | 問題 | 對應設定 |
| --- | --- | --- |
| C1 | 文件的機密等級有幾級？各叫什麼？（例如：公開、內部、機密） | `access.json` 的可見等級 |
| C2 | 有沒有「只有參與某個專案的人才能看」的資料？ | `access.json` 的專案 |
| C3 | demo 要示範哪幾種身分？各能看到哪些等級、哪些專案？ | `access.json` 的角色 |
| C4 | 誰可以上傳新文件？上傳後誰負責確認內容？ | 角色的上傳與審核權限 |
| C5 | 有沒有絕對不能出現在 demo 的資料？（例如：薪資、個資、客戶合約） | 資料盤點表、[資料安全說明](data-security.md) |

## D. 語言與呈現

| # | 問題 | 對應設定 |
| --- | --- | --- |
| D1 | 員工使用哪些語言？文件是用哪些語言寫的？ | `client.json` 的語言 |
| D2 | 有沒有需要跨語言查詢的情況？（例如：用中文問、答案在英文文件裡） | 評測題庫 |
| D3 | demo 的畫面要不要使用公司的品牌色？ | `theme.json` |
| D4 | demo 要用什麼名稱稱呼公司？（demo 一律使用虛構資料，可以用虛構名稱，或經同意後使用真實名稱） | `client.json` 的顯示名稱 |

## E. 成功標準與時程

| # | 問題 | 對應設定 |
| --- | --- | --- |
| E1 | 您認為 demo 回答到什麼程度算「可以用」？ | [驗收指標](acceptance-metrics.md) |
| E2 | 有沒有一定要能正確回答的問題？能否提供 10～20 題，連同正確答案與出處？ | 評測題庫 |
| E3 | 有沒有一定要正確「拒答」的問題？（例如：一般員工問薪資） | 評測題庫的權限題 |
| E4 | 希望什麼時候看到 demo？由誰驗收？ | — |

## 訪談後

1. 整理成一頁摘要，請客戶確認（特別是 C 段的權限設定）。
2. 請客戶依[資料盤點表](data-inventory.md)填寫可以提供的文件。
3. 請客戶閱讀[資料安全說明](data-security.md)，確認 demo 的資料處理方式可以接受。
4. 依摘要建立 `client/` 設定與虛構資料集，再依[評測題庫建立步驟](eval-question-bank.md)出題。
