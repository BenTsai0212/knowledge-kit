# 新增語言步驟

給 coding agent 與決策者使用：為客戶的 demo 加上一種語言（介面、資料與檢索），以及何時需要考慮語意向量。以 #83 的日文實測（暫時客戶 `clients/lang-ja/`）為例。

## 先判斷：語言模組是否已有這個語言的規則

檢索的切詞與上傳的切段，依字元的**文字類別**套用規則，規則只放在語言模組 `app/src/language/`（[docs/retrieval.md](../retrieval.md)「語言模組」）。

| 情況 | 例子 | 要改什麼 |
| --- | --- | --- |
| A. 已驗證 | 繁中（`zh-TW`）、英文（`en`）、日文（`ja`，#83） | 只改客戶資料夾（第 1 節） |
| B. 以空白分詞的語言 | 法文、德文、西班牙文、印尼文、韓文 | 只改客戶資料夾即可運作；但停用詞與去掉字尾 `s` 是英文的規則，檢索品質要以評測確認（第 2 節） |
| C. 不以空白分詞、語言模組還沒有規則 | 泰文、寮文、緬甸文、高棉文 | 選用 A1（`multilingual-e5-small`）時可直接以語意向量檢索與跨語言檢索，不需要先改語言模組，只改客戶資料夾（第 1、4 節）；只用 `keyword-hash` 時，先另開 Issue 修改語言模組（第 3 節），再改客戶資料夾 |
| D. 由右到左書寫 | 阿拉伯文、希伯來文 | 畫面未支援由右到左的版面，屬於程式修改，另開 Issue 討論 |

簡體中文（`zh-CN`）與繁中共用漢字的切詞規則，但停用字是繁體字（例如「這」「們」「與」），簡體的「这」「们」「与」不會被去掉；可以先照 A 做，評測不夠好時再照第 3 節補上簡體停用字。

**落地新客戶時**（[落地新客戶步驟](new-client-setup.md)）遇到 D，或只用 `keyword-hash` 時遇到 C：停下來回報、另開 Issue，不在客戶資料中繞過。

## 1. 客戶資料夾要改的地方

以 `clients/<名稱>/` 為例；`<代碼>` 是 BCP 47 語言代碼（例如 `ja`、`fr`、`zh-CN`）。

1. **`client.json`**：在 `languages` 加上 `<代碼>`；需要時改 `defaultLanguage`（Playwright 以預設語言執行）。
2. **介面文字 `i18n/<代碼>.json`**：從 `en.json` 複製後翻譯，鍵與參數（`{name}` 等）要與其他語言一致，不能缺也不能多（`check:client` 會檢查）。目前約 250 個字串。示範給客戶看的版本要全部翻譯；只做內部驗證時可只翻主要畫面，其餘暫留英文。
3. **各設定檔的多語文字**：顯示名稱、角色、可見等級、專案、實體與關係類型、情境名稱等，每種語言都要填。`check:client` 只檢查預設語言有沒有填，其他語言的缺漏要逐一確認。
4. **實體名稱**：`data/entities.json` 每個實體的 `names` 加上新語言。人名沒有公認譯名時沿用原文，不要自行音譯。
5. **文件**：新增這個語言的文件，`language` 設為 `<代碼>`。段落長度以字元計算，與其他語言相同（`passageMaxChars`）。
6. **預設問題**：`scenarios.json` 每題加上這個語言的問題文字，`answerPassages` 列出答案段落。要求依 `retrieval.provider` 而不同（[落地新客戶步驟](new-client-setup.md)第 3 步）：
   - `keyword-hash` 不支援跨語言檢索，所以每題在新語言都要有同語言的答案段落；沒有對應段落時補寫文件。
   - 語意向量（`multilingual-e5-small`）時，事實可以只寫在一種語言，每題至少一種語言有同語言的答案段落即可。Playwright 用到的兩題要有預設語言的答案段落（[docs/testing.md](../testing.md)「Playwright」）。範例：`clients/kestrova-demo/`（繁中、英文、日文，每個事實只寫在一種語言，#175）。
7. **評測題庫**：依[評測題庫建立步驟](eval-question-bank.md)加入新語言的題目，至少包含權限題與題庫外的題目。跨語言題（以 `passageLanguage` 指定段落的語言）一律標記 `requires: "semantic"`，`keyword-hash` 時不計入分母（[docs/evals.md](../evals.md)「跨語言、同義詞與完全無關的題目」）。

不需要修改：問答 prompt 的語言名稱（以 `Intl.DisplayNames` 產生）、萃取時要求每種語言的名稱、檢索的語言篩選、說法不同只比對同語言、時間軸的語言，這些都依 `client.json` 的語言清單運作。

**驗收**：

- `npm run check:clients <名稱>` 通過。其中 `app/src/retrieval/scenarios.target.test.ts` 會以每種語言檢索預設問題，同語言的答案段落要在前 K 名內。
- Playwright 的客戶格通過（`gh workflow run e2e.yml --ref <分支>`）。
- 選用語意向量的客戶，這兩項都以 `keyword-hash` 檢查，不下載模型（[docs/client-config.md](../client-config.md)「客戶檢查」）；跨語言要靠下一項的評測確認。
- 真實金鑰評測（[驗收指標](acceptance-metrics.md)）中，新語言的題目也要達到門檻。

## 2. 以空白分詞的語言：確認檢索品質

這類語言不改程式也能運作，但目前的規則是為英文設計：

- 英文停用詞（the、is…）套用在所有「其他文字」（拉丁字母、諺文等）上，其他語言的虛詞（例如法文的 le、de）不會被去掉，會稍微拉低分數的鑑別度。
- 去掉字尾 `s` 只適用英文的複數；其他語言的詞形變化（例如德文的格變化、韓文黏在詞尾的助詞）不會處理，同一個詞的不同形態可能對不上。字元特徵（3 字元組）能補回一部分。

做法：先只改客戶資料夾，看第 1 節的檢查與評測結果。答案段落的名次或答案正確率不夠時，再另開 Issue，在語言模組為這個語言加上停用詞或字尾規則（第 3 節的流程）。不要為了通過測試而改寫題目或放寬門檻。

## 3. 語言模組要新增規則時

**先確認是否需要**：選用 A1（`multilingual-e5-small`）時，不以空白分詞的語言（C 類）可直接以語意向量檢索與跨語言檢索，不需要先改語言模組（[docs/retrieval.md](../retrieval.md#語意向量multilingual-e5-small)「語意向量」）。只用 `keyword-hash` 時才需要本節的規則：沒有規則的文字併入「其他文字」，兩個空白之間的一整串成為一個詞，只剩 3 字元組能部分比對，檢索效果很差（[docs/retrieval.md](../retrieval.md#限制)「限制」）。本 template 不內建泰文等語言的規則（[RFC 0002](../rfcs/0002-public-release.md)「修訂紀錄」），需要時在客戶的 fork 依本節實作。

語言模組是所有客戶共用的程式，修改要以獨立的 Issue 與 PR 進行，**不和客戶資料放在同一個 PR**。比照 #83：

1. **開 Issue**（`plan-first`）：說明語言、文字類別，以及要加的規則。
2. **計畫**回答：
   - 文字類別的字元範圍（Unicode 的 Script 屬性）
   - 切詞方式：`bigram`（相鄰兩字一組）或 `segmenter`（`Intl.Segmenter`）。兩種都試，以分數比較；`segmenter` 的結果會隨 ICU 版本而不同，CI、本機與各版瀏覽器可能不一致，分數相近時選 `bigram`
   - 停用詞、句尾標點、換行時是否直接相連
3. **以暫時客戶實測**：在暫時分支（例如 `verify/lang-<代碼>`）建立 `clients/lang-<代碼>/`，內容是參考情境加上新語言，依第 1 節填寫。實測時只能改這個客戶資料夾與語言模組；需要改其他程式就停下來回報。結果與分數比較留言在 Issue，暫時分支不合併，由人刪除。
4. **PR**：只帶回語言模組的規則與單元測試（`app/src/language/text.test.ts`、`app/src/retrieval/tokenize.test.ts`），不放暫時客戶。參考情境（`npm test`）的測試要全部通過、分數不變；結構測試（`app/src/language/structure.test.ts`）確認規則都在語言模組內。
5. 更新 [docs/retrieval.md](../retrieval.md) 的切詞表與實測紀錄，以及本文件第一節的表格。

## 4. 跨語言與語意檢索（第 2 階段）

目前的檢索（`keyword-hash`）比對共同的詞與字元，有兩個與語言有關的限制：

- **不支援跨語言**：中文問題找不到只有英文的段落。所以每種語言都要有自己的答案段落，新增語言時資料集的份量也跟著增加。
- **不懂同義詞**：「主管」找不到只寫「經理」的段落。

客戶在需求確認清單 D2 回答「需要跨語言查詢」，或文件只有一種語言、卻要以多種語言發問時，需要語意向量。換法是替換 `VectorProvider`（[docs/retrieval.md](../retrieval.md)「替換 `VectorProvider`」），檢索、問答與權限的程式不變。三類做法：

| | 瀏覽器內的小型多語模型 | 外部 API | 自架模型 |
| --- | --- | --- | --- |
| 做法 | 在瀏覽器中下載並執行開源的多語 embedding 模型 | 由 Worker 轉發，呼叫模型供應商的 embedding API | 在客戶或我們管理的伺服器上執行開源的多語 embedding 模型 |
| 段落送到哪裡 | 不離開瀏覽器 | **所有段落**（含機密等級）都會送到供應商計算向量 | 只到自架的伺服器 |
| 跨語言與同義詞的品質 | 中等，依模型大小 | 通常最好 | 依選用的模型，可接近外部 API |
| 首次載入 | 要下載模型檔（數十到數百 MB），第一次較慢 | 不需下載；每次計算向量要等網路往返 | 不需下載；要等網路往返 |
| 費用 | 沒有呼叫費用 | 依用量計費，需要新的 secret 與用量上限 | 伺服器與維運的成本 |
| 適合 | demo：資料不出瀏覽器，與[資料安全說明](data-security.md)一致 | 品質優先、客戶同意段落送到供應商 | 正式系統：資料要留在客戶的環境 |

共同的注意事項：

- **先評測再決定**：以同一份題庫分別評測 `keyword-hash` 與候選做法，並加入跨語言題。語意向量的分數分布不同，要一併調整 `minScore` 與 `topK`。
- **權限不變**：段落仍一律經過 `withIdentity()` 取得。向量要存進資料庫時屬於 migration（高風險），要為它設定 RLS，讓看不到段落的身分也看不到它的向量。
- **外部 API**：新增 secret 與相依套件要先問人（AGENTS.md 第 6 節）；機密段落能否送到供應商，要由客戶確認。
- **跨語言題**：題庫的跨語言題標記 `requires: "semantic"`，只在語意向量時計分；驗收時另外列出它們的結果（[驗收指標](acceptance-metrics.md)）。
- 選用的模型、版本與量測結果記錄在 ADR；本文件不列廠商與價格，因為會隨時間改變。
- 2026-11 的評估（#126）：[評估報告](../evals/semantic-retrieval-2026-11.md)、[ADR 0006](../adr/0006-semantic-retrieval.md)（Accepted）。

**已導入的做法**：瀏覽器內的小型多語模型 `multilingual-e5-small`（#163），在 `client.json` 的 `retrieval.provider` 選用（[docs/client-config.md](../client-config.md)、[docs/retrieval.md](../retrieval.md)「語意向量」）。

- 首次載入要下載約 135 MB 的模型，準備失敗時改用 `keyword-hash` 並提示；這時只寫在其他語言的事實檢索不到。客戶的網路可能擋下模型下載時，新語言的段落仍以第 1 節的方式補齊較穩。
- 只靠跨語言（每個事實只寫在一種語言）的實測：`clients/kestrova-demo/`（#175），繁中、英文、日文的跨語言題六個方向共 18 題，引用與答案都 18/18（[評測結果](../../clients/kestrova-demo/evals/README.md#驗收結果)）。
- model card 列出的語言（含 `th`）才考慮只靠跨語言；低資源語言的品質可能下降，先以題庫的跨語言題評測。
- 選用前可先以本機的 `clients/local-<名稱>/` 試用與評測（[docs/retrieval.md](../retrieval.md)「瀏覽器量測」）。
