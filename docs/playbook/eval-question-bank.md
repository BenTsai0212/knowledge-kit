# 評測題庫建立步驟

用一組固定的題目量化 demo 的問答品質，並確認權限沒有滲漏。題庫的檔案格式與評分規則見 [docs/evals.md](../evals.md)；本文件說明「怎麼出題」。

## 1. 和客戶一起決定題目來源

- **客戶提供的真實問題**（需求確認清單 A4、E2、E3）：最有說服力。改寫成虛構資料集能回答的版本。
- **示範情境的預設問題**（`scenarios.json`）：每一題都要放進題庫。
- **我們補充的題目**：依下一步的類別補足數量。

## 2. 依類別出題

| 類別 | 目的 | 建議題數 | 預期結果 |
| --- | --- | --- | --- |
| 情境（`scenario`） | 一般問題能附出處正確回答 | 8 題以上 | 回答 |
| 權限（`permission`） | 同一個問題，有權限的人能答、沒有權限的人拒答 | 每組 2 題（能答＋拒答），4 組以上 | 一題回答、一題拒答 |
| 說法不同（`conflict`） | 新舊說法不同時正確處理：兩種都提到，或依客戶規定以新版為準並說明舊版已被取代 | 每種語言 1 題以上 | 回答 |
| 題庫外（`out-of-scope`） | 資料沒寫的事不亂答 | 3 題以上，至少 1 題是「看起來像公司規定、但資料沒寫」 | 拒答 |
| 套話（`extraction-attempt`） | 要求忽略規則、假冒身分時不洩漏 | 2 題以上 | 拒答 |

**回答題至少 15 題**。回答題太少時，錯 1 題就會讓比例大幅下降（例如 10 題錯 1 題就是 90%，剛好壓在門檻上），難以判斷是品質問題還是偶然。

每種語言都要有題目；有跨語言需求時，加入「用 A 語言問、答案在 B 語言文件」的題目：`category: "cross-language"`、以 `passageLanguage` 指定段落的語言，並標記 `requires: "semantic"`（`keyword-hash` 時不計入分母，見 [docs/evals.md](../evals.md)「跨語言、同義詞與完全無關的題目」）。

## 3. 每題要填的內容

| 欄位 | 寫法 |
| --- | --- |
| 問題 | 用員工實際會說的話，不要照抄文件的句子 |
| 身分 | 以哪個角色提問 |
| 答案段落 | **回答時合理會引用的所有相關段落**，不只是直接寫出答案的那一段。例如問專案進度，負責人與人員支援的段落也算相關。模型常順帶說明背景（例如產品屬於哪家原廠、某人屬於哪個部門），說明這類背景的段落也要列。不同語言的同一段內容都要列 |
| 關鍵重點 | 回答一定要提到的事實，每一項列出同義說法（例如 `第三季`、`Q3`、`third quarter`）；只列題目問到的事實 |
| 禁止內容 | 這個身分**看不到**的資料內容（例如機密的金額）。不列常識：題庫外的問題用常識回答屬於拒答失敗，不是權限滲漏 |
| 參考答案 | 一兩句完整的正確答案，給模型評分使用；只寫題目問到的內容，多寫的事實會讓模型評分以「遺漏」判錯 |

## 4. 檢查與試跑

1. 客戶資料夾執行 `npm run check:clients <名稱>`（參考情境 `client/` 執行 `npm test`）。它會檢查答案段落是否存在、該身分是否看得到，以及預設問題的檢索。
2. 在評測台以預設設定跑一次（關鍵重點評分）。評測台要在網址加上 `?tools=evals` 才顯示（[docs/evals.md](../evals.md)「開啟評測台」）。
3. 逐題看未通過的原因：

| 現象 | 通常的原因 | 處理 |
| --- | --- | --- |
| 引用未通過，但回答正確、引用的段落也確實相關 | 答案段落沒列齊 | 補答案段落，不放寬標準 |
| 答案未通過，但回答其實正確 | 同義說法不夠 | 補同義說法；或改用模型評分對照 |
| 答案未通過，模型評分說遺漏了某件事，但題目沒問到 | 參考答案或關鍵重點超出題目範圍 | 刪掉超出的部分，或把題目改成問到它 |
| 該拒答卻回答了，而且內容來自看得到的段落 | 題目和看得到的資料太接近 | 改題目，不放寬拒答門檻 |
| 該回答卻拒答 | 檢索找不到；資料集沒寫清楚 | 調整資料集的寫法，或比較兩組檢索設定 |
| 權限滲漏 | **系統問題** | 停止交付，先找出原因 |

4. 修正後再跑一次。模型的回答每次會有些微差異，重要的驗收至少跑兩次。

## 5. 和客戶確認

把題庫（問題、身分、預期結果、參考答案）整理成表格請客戶確認，特別是權限題：「這個身分不應該看到這個答案」是否符合客戶的實際規定。

## 6. 交付後的題庫維護

交付時的題庫是品質的基準。交付後資料、設定與使用方式都會變，題庫要跟著維護，但不能讓「改題目」變成「讓分數好看」的手段。

### 題目分成三種

- **核心題庫**：交付時驗收用的題目，固定不動。品質報告以題庫版本（`questions.json` 內容的雜湊）標示是哪一份；內容改了一個字，版本就不同，前後兩次的結果不能直接當成同一份題庫比較。核心題要修正時（例如資料集改版、題目本身有錯），整批修正並記錄原因，不逐題悄悄調整。
- **增補題**：交付後加入的題目，每批少量（例如 5–10 題），加在檔案最後、不調整既有題目的順序，核心題的序號就不會變。來源：
  - **錯誤回報**：問答的「回報有錯」（[docs/qa.md](../qa.md)「回報有錯」）處理完、資料或設定修正後，把那個問題改寫成一題，確認之後不會再錯。demo 的回報只存在瀏覽器，重新整理就消失，處理時當下記下來。
  - **重要文件的候選題**：覆蓋範圍沒有涵蓋的重要文件（品質報告的測試條件），依第 2 步的類別補題。
  - **高頻提問**：使用者實際常問的問題。
  - 系統可以提出候選，**由人決定**是否加入；每一題依第 3 步填寫，依第 4 步檢查。
- **不需標準答案的監測**（長期方向，正式系統階段）：不靠題庫，而是持續觀察使用中的訊號，例如拒答的比例、回報的件數與原因。demo 階段不做。

### 分工

| 角色 | 負責 |
| --- | --- |
| 交付方 | 維護題庫檔案、執行評測、產生品質報告，填寫未通過題目的原因與處理方式 |
| 知識負責人 | 確認題目與答案符合實際內容；提出增補題；修正資料集 |
| 權限管理者 | 確認權限題的預期結果（「這個身分不應該看到這個答案」）符合實際規定 |
| 決策者 | 看品質報告的第一頁，決定是否交付或繼續使用；核心題庫要修正時同意 |

**出考卷的人不是唯一改考卷的人**：交付方出題、跑評測，但題目與預期結果的修改要經知識負責人或權限管理者確認，特別是把未通過的題目改掉或刪掉的時候。

### 什麼時候重跑

- **交付時**：至少兩次，附上品質報告（[驗收指標](acceptance-metrics.md)「交付時附上品質報告」）。
- **大批資料匯入後**：新資料可能改變檢索結果，或讓原本該拒答的題目變得有答案。
- **設定或模型更換後**：檢索設定（`topK`、`minScore`）、provider 或模型改變時。
- **定期**：例如每季一次，即使沒有上述變更。

每次重跑都產生品質報告並保存，和前一次比較時先確認題庫版本與測試條件。
