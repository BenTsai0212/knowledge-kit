# ADR 0011：只審接縫（有把握的直接收錄）

- 狀態：Proposed
- 日期：2026-11-15
- 決定者：@BenTsai0212
- 相關：ADR 0007 決定 8（「有把握的直接收錄」另寫 ADR）、#189（系統先判斷）、#44（待審與核准）、[docs/extraction.md](../extraction.md)「合併」「畫面」、#247

## 背景

#189 之後，待審頁由系統先準備：只有一個候選的合併預先帶入、部門自動合併、圖譜已有的關係只寫決定，這些收合成「系統已準備 N 筆」；但人仍是每份文件的核准者，所有項目都要經過「確認」或「核准這份文件的全部」才進入圖譜。ADR 0007 讓核准可以撤回，為放寬事前審核鋪路，並把「有把握的直接收錄」留給新的 ADR。

人只負責核准時，會傾向全部核准、失去監督能力（[parasuraman2010](../references.md#parasuraman2010)、[bainbridge1983](../references.md#bainbridge1983)）；要求人在迴路中逐筆審核的做法常無法發揮效果（[green2022](../references.md#green2022)）。設計原則是「驗證交給 AI、用評測證明；解讀留給人」：人只處理系統沒把握、需要判斷的地方（接縫），其他直接收錄，錯了靠撤回與回報修正（ADR 0007）。

原型「新 2」（逐筆核准 18 項 vs 只審 2 個接縫、其餘 16 項直接收錄可撤回）的自測（1 人，設計者）：逐筆核准時會想直接按「核准全部」，很難逐筆檢查；只審接縫明確點出矛盾，決策疲勞大幅下降；撤回要明確標示才找得到。

風險：AI 有把握卻錯的項目（原型的 E2：原文是「支援」，萃取成「負責」）會直接進入圖譜，只能靠抽查、撤回與回報發現。

## 選項

- **怎麼判斷「沒把握」（接縫）**
  1. 模型給的數值信心分數：LLM 的自評信心校準不佳，門檻難以說明。
  2. 結構規則：依合併候選數、名稱是否完整、與既有實體名稱是否幾乎相同等可重現的條件判斷。
  3. 結構規則＋模型標示的不確定原因：prompt 要求模型對沒把握的項目附原因類別（例如同名、可能是錯字、關係用詞不明確），只用類別，不用分數。
- **只有一個候選的合併**（會擴大可見範圍，ADR 0007 決定 8 原本維持事前審核）：直接收錄，或列為接縫。
- **沒有 `can_review` 的人上傳時**：直接收錄立即生效，或等有 `can_review` 的人打開待審頁時才收錄。
- **誰寫入直接收錄的決定**：上傳者（新的決定類型 `auto`）、打開待審頁的審核者，或資料庫的系統身分（需要 `SECURITY DEFINER`，與既有原則衝突）。
- **「請上傳者確認」**（原型的出口）：這次做，或之後另開 Issue。
- **開關**：新的 `client.json` 設定，或寫死。

## 決定

1. **接縫用選項 3（結構規則＋模型標示的原因），不使用數值分數。** 下列任一成立的項目是接縫，交給人判斷；其餘直接收錄：
   - 合併候選 2 個以上（兩位林志明）。
   - 名稱缺少語言。
   - 新實體的文件語言名稱，與目前身分看得到的同類型實體只差一個字（正規化後編輯距離 1）：可能是錯字或同一人（原型的「張雅亭／張雅婷」）。
   - 模型標示沒把握（萃取 JSON 新增選填的 `unsure` 欄位，值為 `same_name`、`possible_typo`、`relation_wording`、`other` 之一；不合法的值當作 `other`）。
   - 關係的任一端是接縫時，該關係跟著端點留在接縫中。
   - 說法不同沿用現行流程（[docs/conflicts.md](../conflicts.md)），不在本 ADR 改變。
2. **只有一個候選的合併：直接收錄。** 與 #189 的系統建議一致；合併只能合到上傳者看得到、類型相同的實體（既有 RLS），擴大的是「看得到新文件的人看得到這個實體」。部門的自動合併照舊。
3. **沒有 `can_review` 的人上傳時：萃取完成即直接收錄。** 不等審核者打開待審頁；接縫留在待審。理由：等審核者打開才收錄，只是把核准按鈕換成打開頁面，疲勞來源不變。
4. **寫入方式：上傳者寫入 `auto` 決定。** `review_decisions` 新增 `mode`（`manual`、`auto`）。新增 RLS policy：`mode = 'auto'` 時，`decided_by` 是該文件的上傳者，而且項目不是接縫（資料庫可以檢查的部分：沒有 `unsure`、合併對象看得到且類型相同、名稱完整；合併候選數與編輯距離由 `store.ts` 在同一個交易中重算）。不使用 `SECURITY DEFINER`。
5. **撤回沿用 ADR 0007，並補兩件事**：
   - 待審頁每份文件多一個「已直接收錄 N 項」區塊（預設收合），可以「隨機抽查 3 項」或「展開全部」，每項可撤回。已撤回的項目明確標示「已撤回」。
   - 撤回時選理由（名稱錯了、關係用錯了、不該合併、不該收錄、其他），記在撤回紀錄的新欄位 `reason`（只能新增）。理由供之後的品質報告統計，以及評估接縫規則漏掉了哪些錯誤。
6. **接縫的出口，這次一起做**：
   - 「都不是，我來說明」：審核者自己寫理解（選填），AI 先複述「我理解成…對嗎？」再收下；說明記在決定的新欄位 `note`。
   - 「我不確定，請上傳者確認」：項目維持待審，不計入審核者的待審數字；上傳者的首頁「有更新」收到這個接縫的提問（同樣的選項與「都不是，我來說明」）。上傳者沒有 `can_review`，所以他的回答只是說明，不是決定：回答後接縫回到審核者，附上上傳者的回答與時間，由審核者決定。上傳者就是審核者時，不出現這個出口。
   - 資料：新增只能新增的 `review_requests`（`item_id`、`document_id`、`requested_by`、`requested_at`）與 `review_request_replies`（`request_id`、`replied_by`、`choice`、`note`、`replied_at`）。SELECT：有 `can_review` 且看得到該文件，或是該文件的上傳者且看得到該文件（比照 ADR 0009 的 `own_` policy）。INSERT：請求由有 `can_review` 的人寫入；回答只能由該文件的上傳者寫入，每個請求只能回答一次。
7. **開關：`client.json` 的 `review.mode`**，`"item"`（逐筆核准，現行）或 `"seams"`（只審接縫）。參考情境與線上 demo 用 `"seams"`；`clients/` 的示範客戶各自設定。`"item"` 時畫面與流程與現在完全相同。
8. **接縫的提問方式**照討論版規則：第一人稱、保留語氣，給 2–3 個假設與「都不是，我來說明」，例如「公司有兩位林志明，這份文件提到的是哪一位？」（規則細節在 `docs/design.md`，另一個 Issue）。

## 後果

- **好處**：審核者只處理需要判斷的少數項目；上傳後的內容很快出現在問答與圖譜；撤回理由提供「直接收錄錯在哪裡」的資料，可以回頭改進接縫規則。
- **代價**：
  - AI 有把握卻錯的項目會先進入圖譜，直到有人抽查、撤回或回報；看得到該文件的人會先看到錯的內容。
  - RLS 多一條 `auto` 決定的 policy 與測試；萃取的 JSON 多一個欄位、驗證多一條規則。
  - 沒有 `can_review` 的上傳者實際上可以讓內容進入圖譜（仍只限他能選的可見等級）。需要事前審核的組織改用 `"item"`。
- **限制**：接縫規則是設計者自測與文獻推出的，沒有多人實測；直接收錄的正確率尚未以評測證明。
- **後續工作**（依序各一個 PR）：
  1. 本 ADR。
  2. migration（`mode`、`note`、撤回 `reason`）、RLS 與滲漏矩陣、`store.ts` 的直接收錄與接縫判斷、單元測試。
  3. 萃取 prompt 與驗證的 `unsure` 欄位、`docs/extraction.md`。
  4. 待審頁：接縫區、「已直接收錄」區（抽查、展開、撤回理由）、`client.json` 開關、`docs/design.md`、E2E。
  5. 「請上傳者確認」：`review_requests` 與回答的 migration、RLS、上傳者首頁的提問與回答、待審頁顯示上傳者的回答、E2E。
- **之後另開 Issue**：萃取的評測（以上傳範例的標準答案量直接收錄項目的正確率，作為接縫規則的證據）；品質報告加入撤回理由的統計。
