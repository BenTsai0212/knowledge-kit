# ADR 0013：來源確認（知識負責人確認原文段落）

- 狀態：Proposed
- 日期：2026-11-18
- 決定者：@BenTsai0212
- 相關：#417、ADR 0007（撤回與回報）、ADR 0011（只審接縫）、ADR 0012（人的理解）、[docs/conflicts.md](../conflicts.md)、#247

## 背景

客戶的疲乏來自「每個人每次都要重新驗證」：回答引用的原文是否可靠，每位讀者都得自己判斷一次。研究主線「兩面鏡子」的方向是驗證交給證據、解讀留給人：與其讓 AI 宣稱答案正確，不如讓知識負責人對**原文**確認一次，之後任何回答引用到這段，讀者都看得到「〈角色〉於〈日期〉確認」（「驗證只做一次」）。

要避免的是讓「確認」變成對 AI 回答的背書：越信任 AI 越少批判思考，工作轉向資訊驗證與整合（[lee2025](../references.md#lee2025)）。原文正確不代表 AI 的回答正確，所以確認的對象只能是原文，措辭與外觀都不能讀成「答案正確」。

業界做法的比較：知識庫產品 Guru 的驗證以「知識卡片」為單位，每張卡片有驗證者；重新驗證週期可設 30 天到 1 年或「不會到期」，2026 年 1 月後新建的集合預設為「不會到期」。2026 年 1 月後建立的知識 agent 會依使用者回饋與內容規則每天自動驗證（預設開啟），決定記在「品質紀錄」；agent 也可設定只使用已驗證的內容（[guru-verification](../references.md#guru-verification)）。所以差異不在「有沒有週期」，而在：knowledge-kit 的回答以段落為出處、沒有卡片，而且回答每次重新產生、不保存（`docs/design.md`「首頁」、#247），所以單位是段落；確認只由有 `can_review` 的人做，不自動確認，因為自動判斷的「已驗證」容易被讀成對 AI 的背書；失效來自說法不同，不設週期，避免變成新的待辦壓力。

可沿用的做法：`kk.interpretations`（migration 0015，ADR 0012）以段落為範圍、只能新增、看得到段落才看得到紀錄、只顯示角色與日期。

## 選項

- **單位**：段落；整份文件；回答。回答每次重新產生，保存會違反不保存回答的原則；整份文件太粗，一份文件中常只有部分段落被引用、被確認過。
- **失效**：定期重新確認（有週期、到期提醒）；只在這段出現不同說法時失效。
- **顯示**：回答下方加摘要（「本回答引用的 3 段中 2 段已確認」）；只在引用標號加小標記，詳細資訊放在原文面板。
- **誰能確認**：任何看得到段落的人；有 `can_review`（知識負責人）且看得到段落的人。
- **可否撤銷**：不可撤銷；可撤銷並保留紀錄；可撤銷並刪除紀錄。
- **資料表**：一張表以 `action` 區分確認與撤銷；確認與撤銷分成兩張表（比照 ADR 0007 的撤回紀錄）。
- **失效是否比較先後**：比較說法不同的偵測時間與確認時間（`conflicts` 要新增建立時間）；只看現在的狀態。

## 決定

1. **確認的單位是段落。** 不確認整份文件，也不確認回答。
2. **資料表：一張只能新增的 `kk.passage_confirmations`。** 欄位 `id`、`passage_id`、`action`（`confirm`／`revoke`）、`created_by`、`created_at`、`seq`（同一時間的先後）。一段的**目前狀態**是它看得到的紀錄中 `seq` 最大的一筆：`confirm` 為已確認，`revoke` 或沒有紀錄為未確認。`kk_app` 只有 SELECT、INSERT，沒有 UPDATE、DELETE；不使用 SECURITY DEFINER；不修改 `kk.passages`。
3. **誰能確認、誰能撤銷：有 `can_review` 而且看得到那一段（RLS）。** 確認與撤銷是同一條 INSERT 規則：`created_by` 是自己、`created_at = now()`、那一段看得到。參考情境原有的段落也可以確認（新增紀錄，不修改內容）。資料庫不擋「沒確認就撤銷」或「重複確認」，畫面只在對應狀態顯示按鈕；多一筆不影響狀態。
4. **撤銷**：撤銷後畫面回到「未確認」，紀錄保留（畫面不列歷史）。
5. **誰看得到確認紀錄：看得到那一段的人**（比照 `interpretations` 的 `can_see`）。畫面只顯示角色與日期，不顯示名字。看不到那一段的身分看不到任何確認的痕跡。
6. **失效只來自說法不同，依目前身分看得到的 `conflicts` 與 `conflict_decisions` 判斷：**

   | 這段所在的說法不同 | 顯示 |
   | --- | --- |
   | 沒有，或全部處理為「不是說法不同」（`not_conflict`） | 已確認（有效） |
   | 處理為「以新的為準」（`supersede`），這段是舊的一段 | 失效：「已確認，但已被新的說法取代」，連到新的一段 |
   | 處理為「以新的為準」，這段是新的一段 | 已確認（有效）：主管已決定以新的為準，再標「有不同說法」會和這個決定矛盾 |
   | 處理為「並存」（`coexist`）或尚未處理，兩端都是 | 失效：「已確認，但有不同說法」，連到另一段 |

   一段屬於多組說法不同時，取最嚴重的一種（被取代 > 有不同說法 > 有效）。尚未處理的說法不同只有 `can_review` 看得到（migration 0008 的 RLS），所以一般員工在主管處理前看到的仍是「已確認」，處理為並存或取代後才看到失效；這是現有的可見範圍，不另外透露。
7. **不比較先後，不新增 `conflicts` 的建立時間。** 失效只看現在的狀態，不看確認與偵測誰先：在知道有不同說法後才確認，原文仍然有另一種說法，顯示「有不同說法」才誠實；說法不同的狀態改變時，確認的顯示跟著變，不必記住歷史；也不必為了比較新增 migration 修改 `conflicts`。
8. **顯示**：
   - 原文面板：能確認的身分在段落旁看到「確認這段」，已確認時改為「撤銷確認」；段落下方與「記錄」同一區顯示「這段原文已確認 · 〈角色〉於〈日期〉確認」；失效時同一區顯示第 6 點的說明與連結。
   - 回答的引用標號：只在引用到**有效**的已確認段落時加小標記，`markText` 的 5px 實心圓點（仍屬證據色系，客戶不能改，不新增 token），`aria-label` 為「引用 N，這段原文已確認」；失效時不加（說法不同已有洋紅的提示）。不用 `success` 綠、不用勾勾，避免讀成「答案正確」。回答下方不加摘要。
   - 品質報告：評測引用的段落中已確認（有效）的比例，分子與分母都只算報告產生者看得到的段落；列在附錄，不設門檻、不影響通過與否。
9. **措辭界線**：一律說「這段原文已確認」，不說「答案已確認」或「已驗證」。
10. **確認只顯示，不改變回答**：不影響回答內容、檢索排序與 prompt。
11. **不做**：定期重新確認與到期提醒、整份文件確認、確認清單頁、確認 AI 的回答。

## 後果

- **好處**：知識負責人確認一次，所有看得到那一段的人都受益，不必各自重新驗證；確認附在原文而不是回答上，不保存回答、也不替 AI 背書；失效跟著說法不同的處理自動變化，不產生新的待辦。
- **代價**：多一張資料表、RLS 與滲漏測試；原文面板與引用標號各多一種狀態；說法不同處理為並存後，就算主管重新確認，畫面仍顯示「有不同說法」，要解除只能把那一組處理為「不是說法不同」。
- **限制**：
  - 確認只代表「確認者當時認為這段原文正確」，不代表內容之後仍正確；沒有週期，原文過時但沒有新文件提出不同說法時，確認會一直有效。
  - 角色層級的身分，同角色的人看不出是誰確認的。
  - 紀錄只存在瀏覽器的記憶體資料庫，重新整理即消失（與其他寫入相同）。
  - 研究主線與 Guru 的比較沒有多人實測；功能上線並試用後再改為 Accepted。

  4. 引用標號的小標記、品質報告的確認比例、`docs/qa.md`、`docs/evals.md`、`client/i18n/`，附畫面的 E2E 截圖（1440、390）。

## 設計依據

- 驗證交給證據、解讀留給人；疲乏來自每次重新驗證：研究主線「兩面鏡子」→ 研究討論
- 確認原文而不是回答、不用「正確」的外觀：越信任 AI 越少批判思考 [lee2025](../references.md#lee2025) → 文獻
- 以段落為單位、只由 `can_review` 的人確認（不自動確認）、失效來自說法不同：與 Guru 以卡片為單位、可設週期或不到期、有知識 agent 自動驗證的比較 [guru-verification](../references.md#guru-verification) → 業界產品
- 只能新增、看得到段落才看得到、只顯示角色與日期：ADR 0012 的 `interpretations` → 專案規則
- 不保存回答、不透露看不到的內容：`docs/design.md`「首頁」、#247 → 專案規則
